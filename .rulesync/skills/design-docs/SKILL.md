# 正式游戏设计

把已确认决策写入当前有效的游戏设计权威源。入口统一，但概念、系统和功能仍按模式分开维护，避免生成巨型单文件文档。

## 权限边界

- **可写权威**：已确认的概念与体验承诺、`SYS-*` 系统边界与产品 MVP、`RULE-*` 功能规则与行为验收。
- **只读输入**：`EVID-*`、`DEC-*`、用户确认、现有设计、实现约束与项目治理信息。
- **禁止越权**：不自行调查证据、不比较候选、不替用户拍板、不写里程碑治理；不提供独立数值体系、独立 UI 策划案或评审报告。
- **必要内联信息**：规则成立所必需的常量、输入、反馈和显示要求可以写入对应 `RULE-*`，但不扩成独立数值模型或页面规格。
- **条件模块边界**：reference 只补充已确认结论、规则字段与预设观察信号；出现互斥方案时转 `design-inference`，需要竞品、试玩、访谈、指标、日志或实现调查时转 `design-evidence`。

## 模式选择

一次请求默认只有一个主模式和一个主要产物。跨层请求先修改最高层且真正发生变化的权威，再列下游同步任务。

| 模式 | 回答什么 | 可写范围 | 必读 reference |
|------|----------|----------|----------------|
| `concept` | 游戏是什么、给谁玩、承诺什么体验 | 目标玩家、幻想、支柱、核心动作循环、顶层边界 | `references/concept.md` |
| `system` | 由哪些系统承载、产品 MVP 包含什么 | `SYS-*`、职责、依赖、P0-P3、产品 MVP、定性资源拓扑 | `references/system-map.md` |
| `feature` | 单个系统或功能如何运作 | `RULE-*`、对象、流程、状态、事件、不变量、异常恢复、验收 | `references/feature-rules.md` |

不要在同一执行上下文加载或处理三个模式。用户明确要求 `full-package` 时，由 `design-workflow` 编排 `concept → system → feature` 三个独立子任务或后续任务；每个任务只加载一个模式文件及命中的条件 reference，并只交接稳定 ID、上游版本、`DEC-*` / `EVID-*` 引用、未决项和下游目标。三个任务完成后只更新 `INDEX.md` 的摘要、状态与链接，不生成单文件正文汇编。

## 共同流程

1. **确认模式与上游**：定位要修改的权威层级、已有文档、`DEC-*` 和证据引用。
2. **检查是否已收束**：仍有互斥候选时转 `design-inference`；阻塞级分支未确认时按 `design-workflow` 的门禁使用 `grill-me`。
3. **差量修订**：已有权威源时只修改受影响章节或稳定 ID，不为套模板重写全文。
4. **保持层级边界**：概念不提前写系统细节，系统不提前写内部规则，功能不重新定义上层方向或系统边界。
5. **给出可观察验收**：验收只覆盖本次实际规则与边界，不附全量审计矩阵。

## 输出档位

读取 `../design-workflow/references/artifact-output-profiles.md`：

- 咨询、单一判断或局部差量使用 `brief`。
- 正式创建或修订一篇设计产物使用 `standard`。
- 明确交实现时，只有 `feature` 模式使用 `implementation-ready`。
- 明确要求完整归档包时先交 `design-workflow`，由治理任务持有 `full-package` 档位；隔离后的当前设计子任务仍按用途使用 `standard` 或 `implementation-ready`，只生成一个模式文件和最小交接索引。

每篇正文只包含当前模式的核心骨架和真正命中的条件模块；未命中模块直接省略。命中多个条件 reference 时按当前章节逐个加载，不做全量预读。

## 完成标准

- 每项正式结论能追溯到用户确认、`DEC-*` 或证据。
- 当前任务只有一个模式、一个主要产物和一个最小交接索引，没有把三种模式拼进同一上下文或巨型文档。
- 概念、系统和功能的稳定 ID 与上下游引用清楚。
- 未确认内容明确标注，没有被包装成当前有效规则。
