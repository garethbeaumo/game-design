# 项目支柱与概念边界

用于把已确认的体验方向写成可指导取舍的概念支柱，并明确项目级“必须提供 / 延后 / 不提供”。本文件不分配 P0-P3、不制定版本排期，也不决定资源或人员优先级；这些分别属于 `design-docs:system` 与 `design-workflow`。

## 支柱写法

支柱优先描述玩家动作与体验取舍，不写空泛题材词。

| 字段 | 要求 |
|------|------|
| 支柱 | 3～5 条，能由团队复述 |
| 玩家行为 | 玩家会反复做什么、比较什么或追求什么 |
| 意味着什么 | 对后续设计的正向约束 |
| 不意味着什么 | 明确不服务的反向方向 |
| 依据 | 用户确认、`DEC-*` 或 `EVID-*` 引用 |

## 概念边界

- **必须提供**：缺少就无法兑现核心体验承诺的项目级能力，不展开承载系统。
- **可以延后**：不改变一句话概念与核心动作循环、可后续验证的方向。
- **明确不提供**：会分散核心行为、破坏信任或把项目带向另一种产品的方向。
- **不可牺牲体验**：即使缩小范围也必须保留的玩家感受和行为。

概念边界回答“产品为什么仍是这个游戏”，不是系统清单。需要判断最小闭环、系统优先级或 P0-P3 时转 `design-docs:system`。
