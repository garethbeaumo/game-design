# `feature` 模式：功能与系统规则

为一个具体 `SYS-*` 或边界清楚的功能定义可实现、可验收的行为规则。

## 权限

- 写入 `RULE-*`、对象与字段语义、触发条件、流程、状态、事件、不变量、优先级、异常恢复、内容对象结构和行为验收。
- 概念、`DEC-*`、`SYS-*`、产品 MVP、玩家证据和实现约束是只读上游。
- 不修改上层体验或系统边界，不指定程序架构、类名或目录。
- 规则成立所需的常量、输入、反馈和显示要求可以内联；不扩成独立数值体系或 UI 页面方案。

## 工作原则

- 一次只处理一个系统或清晰功能切片；每条 `RULE-*` 只表达一个触发、结果或限制。
- 先说明问题、目标行为与不做什么，再写规则。
- 新系统或多候选方案先由 `design-inference` 形成 `DEC-*`；系统边界不清时回 `system` 模式。
- 上游只通过稳定 ID 或链接引用，不复制全文。
- 目标、范围、核心规则或跨系统边界仍有阻塞分支时使用 `grill-me`。

## 按需读取

只有相应问题会改变本次 `RULE-*` 时才读取：

- 实现交接：`feature/execution-handoff.md`
- 玩家错误、失败归因与风险回报：`feature/player-error-psychology.md`
- 谜题、能力门槛与提示梯度：`feature/competency-puzzle-challenge.md`
- 瞄准、QTE、命中框与操作手感：`feature/input-precision-control.md`
- 教程、关卡、任务、节奏与心流：`feature/experience-pacing-flow.md`
- PVP、合作、阵营、交易与克制：`feature/strategic-interaction-payoff.md`
- 目标玩家、动机、可访问性、主题或 MDA：读取 `concept/` 下对应 reference，但只把已确认约束落为功能规则。

## 上下文

1. 读取 `SYS-*` 职责、依赖、产品优先级和相关 `DEC-*`。
2. 读取同名功能案、相关 `RULE-*`、测试证据和实现事实。
3. 核对本次规则是否仍在系统边界内；越界内容先回上层处理。
4. 当前实现只作为 `FACT-*`；未确认代码或原型是伪约束候选。
5. 已有文档只修改受影响的规则、对象、状态、事件和验收。

## `standard` 核心骨架

1. **背景与目标**：问题、目标行为、可验证结果和上游引用。
2. **范围**：包含、不包含和明确延后行为。
3. **对象语义**：对象、身份、职责、生命周期和必要字段。
4. **核心规则**：`RULE-*` 的触发、条件、结果、限制和优先级。
5. **流程、状态与事件**：进入、退出、切换、中断、失败、取消、重试、不变量和非法组合；简单线性流程不强行建表。
6. **跨系统接口**：依赖、共享状态 / 事件和责任归属。
7. **行为验收**：正常、边界、失败和恢复路径的可观察结果。
8. **待确认问题**：只保留会改变规则、范围、状态或验收的阻塞问题。

## 条件模块

- 教学、挑战与精确输入：能力前提、操作语义、失败恢复和验证位置。
- 复杂对象与并发：对象关系、事件顺序、不变量、优先级和非法状态。
- 策略互动：合法行动、信息可见性、反制机会、专精语义和重置行为。
- 内容对象：类别、字段语义、主键 / 引用、必填性、入口、生命周期和代表性样例。
- 语义反馈：玩家必须知道的事件、原因、结果和下一步，不设计完整页面。
- 玩家保护：确认、取消、恢复、替代输入和不可逆行为保护。
- 实现交接：仅在 `implementation-ready` 时读取交接 reference，补状态事件、数据语义、资源影响和验证点。

## 自检

- 规则是否在 `SYS-*` 边界内并能追溯到上游目标。
- 对象、流程、状态、事件、不变量和恢复是否闭环。
- 每条规则是否有唯一触发、结果和可验证边界。
- 是否把实现架构、独立数值模型或完整页面方案误写进规则案。
