# `playtest` 模式：试玩、反馈与指标归因

用于分析试玩、用户测试、录像、访谈、问卷、社区反馈、埋点、线上指标或 A/B 结果。目标是说明发生了什么、证据有多强和最可能的归因，而不是直接修改设计。

## 权限

- 写入 `TEST-*` / `EVID-*`：原始证据索引、样本与版本、归因假设、证据强度、验证结论和回归方案。
- 被测设计、实现和里程碑均为只读输入。
- 单条意见、相关性或异常指标不得直接写成新规则；需要改变方案时交 `design-inference`，已有明确结论的局部修订交 `design-docs`。

## 工作原则

- 先固定测试目的：首次体验、自然行为、功能验证、回归、负载、线上验证或商业假设。
- 反馈不是结论；回到行为、样本背景、测试情境和目标玩家匹配度。
- 小样本可以发现问题，不能证明比例；指标可以发现变化，不能自动解释原因。
- 首次体验只能由未玩过当前版本的目标玩家证明；复用玩家只证明回归、节奏或流畅度。
- 先检查产品、测试情境、玩家状态与目标玩家不匹配，再提出下一轮验证方向。

## 按需读取

- 测试方法、首次体验漏斗、证据强度和指标解释：`evidence-attribution-methods.md`。
- 可访问性、设备与环境差异作为样本和测试条件分层记录；不加载正式设计 reference 来生成设计回应。
- 致命假设失败后需要重新比较方案：转 `design-inference`。

## 流程

1. 记录测试目标、方法、目标玩家、样本、版本、环境和干预程度。
2. 分开整理行为、话术、情绪、用时、失败点、路径、日志与指标，并保留反例。
3. 建立归因候选：目标、Sign、Feedback、输入、规则理解、节奏、动机、Bug、性能、测试情境或样本不匹配。
4. 标记强 / 中 / 弱证据；线上指标必须结合漏斗、路径、分群、版本差异或访谈解释。
5. 给出与归因匹配的验证方向，并区分立即复查、下轮验证和继续观察；不在证据报告中决定设计改法。
6. 写明回归问题、观察证据和结论被推翻时的处理方式。

## `standard` 输出

- 测试目标、方法、版本、样本和关键限制。
- 关键发现及可复查证据。
- 观察 / 证据 / 归因假设 / 强度 / 影响 / 验证方向。
- 验证结论：通过 / 需调整 / 需重测 / 假设失败 / 阻塞。
- 回归计划与后续路由。

指标、首次体验、设备差异和完整原始证据附录仅在命中时展开。

## 自检

- 是否区分行为、自述、指标和设计师判断。
- 是否避免用小样本证明比例或用相关性证明因果。
- 是否先检查产品表达与测试条件，而不是归咎玩家。
- 是否只提出归因假设和验证，没有选择设计改法或直接改写正式设计。
