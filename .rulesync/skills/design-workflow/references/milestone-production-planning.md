# 里程碑与制作规划

用于版本路线、里程碑、Sprint / 阶段计划、团队交接和制作推进。目标是让每个阶段证明一个明确结果，而不是只排日期或列愿望清单。

需要处理共享愿景、决策权或跨工种冲突时，继续读取 `team-collaboration-governance.md`。

## 使用原则

- 里程碑验证明确目标：核心循环、可玩切片、内容产能、技术风险、上线质量或产品假设。
- 出口必须有可观察证据，不能只写“完成若干功能”。
- 先保护高频核心体验，再安排表现、内容量和扩展能力。
- 快 / 好 / 便宜通常只能优先两个；计划必须写清牺牲项。
- 新增人力不会自动缩短关键路径，沟通、交接和集成成本进入风险判断。
- 产品 MVP 与 P0-P3 由 `design-docs:system` 定义；本文件只把已确认范围安排到制作阶段。

## 常见阶段

| 阶段 | 目标 | 退出证据 | 不应追求 |
|------|------|----------|----------|
| 概念探索 | 确认游戏是什么、给谁玩、为何值得做 | 概念、决策与关键证据 | 完整系统与内容清单 |
| Prototype | 验证致命假设 | 原型、观察与通过 / 失败标准 | 正式内容量和最终表现 |
| Vertical Slice | 证明目标品质和跨工种流程 | 一段可玩切片、资源管线与集成检查 | 长线内容铺量 |
| MVP | 最小闭环可反复游玩 | P0 系统闭环、基本反馈与会话边界 | P2/P3 深度和长期扩展 |
| Alpha | 功能范围基本锁定 | 主要系统可玩、缺陷与内容缺口清楚 | 大规模新增系统 |
| Beta | 内容和质量收敛 | 回归、性能、稳定性和目标玩家证据 | 重新定义核心体验 |
| Release | 达到发布条件 | 阻塞清零、版本说明与风险预案 | 新设计探索 |

## 里程碑字段

| 字段 | 要求 |
|------|------|
| 里程碑名称 | 用目标命名，如“核心战斗灰盒验证” |
| 阶段目标 | 本阶段要证明或交付什么 |
| 可玩结果 | 玩家或验收者能实际操作到什么 |
| 范围边界 | 引用已确认的 P0 / P1 / 延后 / 不做 |
| 策划产物 | 证据、`DEC-*`、概念、系统地图或功能规则 |
| 实现与资源 | Unity 功能、场景、Prefab、配置、表现、音频、工具或数据 |
| 验证方法 | Prototype、试玩、编辑器检查、Console、目标测试或人工检查 |
| 角色 | 负责人、最终审批者、被咨询者和被通知者 |
| 关键路径 | 不能并行或会阻塞后续工作的依赖 |
| 风险与回退 | 触发信号、影响、处理和回退方案 |
| 出口标准 | 可复查证据，不能只写“完成” |

## 关键路径检查

- 是否有一个未验证假设阻塞多个系统。
- 是否有资源、工具、配置或场景引用阻塞多个工种。
- 是否把需要先验证的核心手感、控制或反馈延后过晚。
- 是否把必须串行的任务写成并行。
- 是否有权威源或最终决策权未定，导致实现无法开工。

## 范围处理

需要保留、简化、延后或删除设计内容时：

- 产品范围与 P0-P3 由 `design-docs:system` 修订。
- 里程碑时间、关键路径和资源安排由 `design-workflow` 修订。
- 仍需比较方案时先由 `design-inference` 形成 `DEC-*`。
