# 五 Skill 路由与权限矩阵

本文件同时回答“谁负责”和“能写什么”，是策划 Skill 职责的唯一口径。交付深度查看 `artifact-output-profiles.md`，阶段门槛与所需证据索引查看 `stage-gates.md`。

## 权限矩阵

| Skill | 唯一主触发 | 可写权威 | 只读输入 | 禁止越权 |
|-------|------------|----------|----------|----------|
| `design-workflow` | 下一步、路线、里程碑、策划产物状态、阶段门槛、归档、完整包编排、入口边界、决策角色 | `GOV-*`、计划、索引、风险、阶段门槛判定与证据索引 | 所有专项产物的状态和依赖 | 不写事实、方案取舍、玩法状态机、P0-P3、产品 MVP 或游戏规则 |
| `grill-me` | 阻塞级分支尚未达成共享理解 | 会话内确认摘要，不形成正式权威 | 已有证据、候选与约束 | 不替用户拍板，不写正式产物，结束后回原 Skill |
| `design-evidence` | 竞品、试玩或实现原始材料需要调查 / 归因 | `COMP-*`、`TEST-*`、`FACT-*`、`EVID-*` | 项目背景与设计仅用于确定问题 | 不决定采纳，不选择设计改法，不写 `DEC-*` 或正式设计 |
| `design-inference` | 已有证据，需要界定设计问题、比较候选或形成决定 | `DEC-*`、假设、取舍、Prototype | 已固化证据和现有设计 | 不分析尚未固化的原始材料，不把推荐直接写成当前规则 |
| `design-docs` | 已确认结论需要创建或修订正式设计 | 概念、`SYS-*`、P0-P3、产品 MVP、`RULE-*` | `EVID-*`、`DEC-*`、用户确认与实现约束 | 不自行取证、比较候选或写治理计划 |

## 主路由

| 用户真正要解决的问题 | 主责 Skill | 模式 | 唯一产物 |
|----------------------|------------|------|----------|
| 下一步、文档链、里程碑、状态、归档、谁拍板 | `design-workflow` | `governance` | 路线或治理产物 |
| 同时跨概念、系统、功能的完整归档包 | `design-workflow` | `governance` | 隔离任务链与最小交接索引；输出档位为 `full-package`，各任务再交 `design-docs` 单一模式 |
| 高影响互斥分支需要问到共享理解 | `grill-me` | `grill` | 确认摘要，随后交回原 Skill |
| 竞品怎么做、是否可比、体量或市场事实 | `design-evidence` | `competitor` | 竞品证据报告 |
| 试玩、反馈、指标、录像或 A/B 原始结果说明什么，包括“问题出在哪” | `design-evidence` | `playtest` | 测试证据与归因报告 |
| 代码、场景、Prefab、配置或原型实际如何工作 | `design-evidence` | `implementation` | 实现事实报告 |
| 基于已有 `EVID-*`，设计问题应如何界定、要不要做、选哪个方案、如何收束 | `design-inference` | `decision` | `DEC-*` 或 Prototype 计划 |
| 游戏是什么、给谁玩、承诺什么体验 | `design-docs` | `concept` | 概念案或概念差量 |
| 有哪些系统、谁负责、产品 MVP 包含什么 | `design-docs` | `system` | 系统地图或产品 MVP |
| 单系统或功能如何触发、流转、结束和验收 | `design-docs` | `feature` | 功能规则案或规则差量 |

## 模式规则

### `design-evidence`

- 一次只选 `competitor`、`playtest`、`implementation` 之一。
- 混合材料按证据问题选主模式；其他材料只作旁证。
- 只要主要输入仍是原始试玩、反馈、指标、录像或日志，先走 `playtest`；“判断问题出在哪”不会把它升级为设计决策。
- 证据足够后，需要判断如何处理才转 `design-inference`；不得在报告末尾偷偷完成决策。

### `design-docs`

- 概念承诺改变：`concept`。
- 只改变系统职责、依赖、P0-P3 或产品 MVP：`system`。
- 只改变系统内部对象、规则、状态、事件或验收：`feature`。
- 跨层请求先选真正发生变化的最高层权威；其他层只列同步任务。
- 用户明确要求完整包时先回 `design-workflow` 编排隔离任务；当前 `design-docs` 任务仍只处理一个模式和一个主要产物。

## 常见冲突裁定

| 冲突 | 裁定 |
|------|------|
| `design-evidence` vs `design-inference` | 原始材料先由前者回答事实、归因假设与可信度；后者只基于已固化证据界定设计问题并决定项目如何选择 |
| `design-inference` vs `design-docs` | 前者保存候选、取舍与验证，后者只保存已确认的当前设计 |
| `design-workflow` vs `design-docs:system` | 前者维护时间、人员、里程碑、阶段门槛判定与证据索引；后者维护系统 P0-P3 与产品 MVP |
| `design-docs:concept` vs `system` | 核心体验、玩家和动作循环归概念；承载这些承诺的系统集合归系统 |
| `design-docs:system` vs `feature` | 系统职责、依赖和产品范围归系统；内部流程、状态与事件归功能 |
| `grill-me` vs 其他入口 | 自动插入时只处理原 Skill 已定位的阻塞分支；用户明确要求拷问时可直接使用，确认完成后返回正在讨论的设计入口 |

## 当前不提供的专项入口

- 独立数值模型、经济曲线和配置体系。
- 独立 UI 页面、控件和交互策划案。
- 独立文档评审、平衡检查、范围检查和变更影响报告。

规则成立所必需的常量、输入、反馈和显示要求可以由 `design-docs:feature` 内联；不得因此重建被删除的专项 Skill。
