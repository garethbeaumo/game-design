# 阶段门槛与完成定义

本文件只回答“是否有足够证据进入下一阶段”。它是治理检查，不是独立评审产物，也不替专项 Skill 修正文档。

## 判断规则

- 每条结论指向可复查证据：文档、章节、稳定 ID、测试记录、命令结果或编辑器检查。
- 证据缺失时标“未证明”，不能默认通过。
- 未触发的条件模块属于范围外，不能为了模板完整升级文档。
- 外部事实通过引用满足门槛，不复制全文。
- 默认只输出阻塞、限制和未证明项；不附全量检查矩阵。

## 状态

| 状态 | 含义 |
|------|------|
| 通过 | 证据足以进入下一阶段 |
| 有条件通过 | 无阻塞项，但有限制、负责人和关闭条件 |
| 未通过 | 证据明确表明要求不成立 |
| 未证明 | 证据不足或不可复查 |
| 不适用 | 已说明为何不属于当前范围 |

## 证据 → 决策

必须证明：

- 证据问题、对象、版本、日期、样本或实现来源明确。
- 观察、推断和未知项分开，关键事实可复查。
- 证据强度、可比性、复现条件和局限明确。
- 报告没有替项目作方案选择，待决策问题可定位。

## 决策 → 正式设计

必须证明：

- 决策问题、所属层级和正式落点明确。
- 关键约束有来源和证据状态，主要候选存在真实差异。
- 推荐方案、放弃项、反选代价和回退条件可复查。
- 致命假设有最小 Prototype、观察证据和通过 / 失败标准，或已说明无需 Prototype。
- 阻塞分支已经确认，或存在带验证时机的显式默认。

## 概念 → 系统地图

必须证明：

- 目标玩家、体验承诺、3～5 条支柱和核心动作循环可被复述。
- 必须提供、明确不提供与不可牺牲体验边界清楚。
- 每个 `SYS-*` 能追溯到循环节点或顶层承诺，并只有一个主职责。
- P0-P3 与产品 MVP 由系统地图唯一维护，P0 足以形成最小闭环。
- 输入输出与依赖清楚，没有未解释的循环依赖。

## 系统地图 → 功能规则

必须证明：

- 目标 `SYS-*` 的职责、依赖、优先级和本次功能边界稳定。
- 功能切片不需要重新决定概念、系统集合或产品 MVP。
- 必需的 `DEC-*`、`EVID-*` 和上游接口可定位。
- 缺失项已经标为阻塞或后续任务，没有被临时猜测填平。

## 功能规则 → 实现交接

必须证明：

- `RULE-*` 覆盖触发、条件、结果、限制、流程、状态、事件、不变量和失败 / 恢复路径。
- 对象身份、字段语义、引用和生命周期清楚。
- 跨系统依赖、共享状态 / 事件、实现消费方和资源影响可定位。
- 验收覆盖正常、边界、失败和恢复路径，并能观察玩家目标行为。
- 明确进入实现时，才要求存档兼容、Unity 资源影响和编辑器 / 测试验证方式。

## 制作推进总门槛

- 必需的证据、决策与正式设计均可定位，阻塞项清零。
- 重要限制有负责人、关闭条件和最晚确认时机。
- 涉及 Unity 的交接有与风险相称的编辑器、Console、目标测试或人工检查计划。
- 负责人或指定审批者已经记录是否允许进入下一阶段；Skill 不自行批准。
