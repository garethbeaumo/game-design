# 策划 Skill 路由与组合

本文件属于策划 Skill 外部控制面，不复制进任何运行时 Skill。日常工作从“用户这次已授权改变、证明或治理什么”出发，不从完整 GDD 层级出发；策划 Skill 自身的创建、重构、评测和生成维护由通用 Skill 工具处理，不路由到这四个游戏策划 Skill。

## 总触发门槛

只有主要对象是游戏设计，并且普通直接回答不足以完成时，才进入策划 Skill。阅读、总结、翻译、格式整理、简单查询、休闲讨论、代码修复、普通技术项目管理和 Skill 自维护直接处理。

## 四个入口

| Skill | 唯一主责 | 不负责 |
|-------|----------|--------|
| `design-docs` | 新增、修改、拆分、合并或废弃当前概念、系统注册项和功能规则 | 多源调查、高影响候选取舍、跨版本治理 |
| `design-evidence` | 需要复查或长期引用的竞品、试玩/指标和实现事实 | 选择方案、确认规则 |
| `design-inference` | 真实候选、高影响或高返工成本的评审、取舍、Prototype 计划及基于证据的候选决定 | 原始材料和 Prototype 结果调查、直接写当前规则 |
| `design-workflow` | 游戏版本范围、多人责任/审批、关键路径、迁移窗口、发布，以及从当前权威生成只读快照 | 纯设计结构拆并、单项事实、候选取舍、游戏规则、Skill 自维护 |

## 默认路由

| 用户真正要完成的事 | Skill / 模式 |
|----------------------|--------------|
| 新写或修改玩家承诺、设计支柱、核心循环 | `design-docs:concept` |
| 新增、拆分、合并、废弃系统，或维护职责/接口/依赖 | `design-docs:system-map` |
| 新写或修改某个系统的对象、规则、状态、事件、数值/反馈约束和验收 | `design-docs:feature` |
| 多源研究具体竞品或品类设计 | `design-evidence:competitor` |
| 分析试玩、访谈、社区反馈、遥测、指标或 A/B | `design-evidence:playtest` |
| 从代码、场景、Prefab、配置或运行结果反推实际行为 | `design-evidence:implementation` |
| 比较达到高影响或高返工升级门槛的真实候选、形成推荐或最小 Prototype | `design-inference:decision` |
| 协调游戏版本/多人责任、关键路径、迁移窗口、里程碑或发布 | `design-workflow:governance` |
| 按当前权威生成完整 GDD / full-package 或评审快照，不增加新事实 | `design-workflow:snapshot` |

“帮我设计 XX 系统”默认创建可讨论的 `proposed + unverified` 功能规则；只有用户要维护系统职责和依赖时才同步 `system-map`。草案不等于已经确认。

## 按风险升级，不走固定流水线

- 普通局部变化直接由 `design-docs` 差量处理，不强制先产出 `EVID-*` 或 `DEC-*`。
- 关键事实缺失且会改变结论时，先用 `design-evidence`；若用户已授权后续判断或落档，完成证据后继续交接。
- 候选取舍达到 `design-inference` 的高影响或高返工门槛时再升级；普通默认和低风险细节在当前变化中内联判断。
- 只有游戏依赖、人员、版本、迁移或发布出口需要统一协调时才使用 `design-workflow`。
- 明确等待未来用户确认的步骤不属于当前路由；确认后再重新计算受影响范围。
- 一次 change-set 可以按需要组合多个 Skill，但每一步只写自己拥有的内容。
- 活跃 change-set 委托证据或取舍后，有限结论直接返回 `design-workflow` 继续范围、门槛或发布治理；只有同时要改游戏规则时才另交 `design-docs`。这是返回发起者，不是新增固定阶段。

## 冲突裁定

- 需要专项复查、复现或长期引用的事实由 `design-evidence` 固化；普通直接来源在当前变更中内联依据与局限。
- `design-docs` 可以创建 `proposed` 提议，也可记录明确采用但尚待验证的 `current + unverified`；没有采用来源时不得标为 `current`。
- 代码与设计不一致时，先调查实际行为，再决定修实现还是接受新行为；两者都不能自动覆盖对方。
- 系统结构归 `design-docs:system-map`；某版本纳入哪些系统、P0-P3、人员和日期归 `design-workflow`。
- 完整快照只投影实际可定位的现有权威及其状态、来源和未知项；没有权威正文或路径时简洁报告来源缺口并停止，不得把不可见误判成未登记，也不得凭空补负责人、日期、门槛、回退、change-set 或成套空表。
- UI、数值和经济若是玩家可见行为规则的一部分，可写入 `feature`；视觉稿、控件实现、配置生成或代码不进入本套件。
