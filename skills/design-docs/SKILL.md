# 迭代式游戏设计写入

把一次新增、修改或删除记录为可区分的提议、当前规则或替代关系。默认修改最小必要范围；没有现成文档时只创建能承载本次变化的最小切片，不为套模板补齐整套策划案。

## 两维状态

当前性与验证性回答不同问题，必须分开记录。

在 YAML、表格或其他结构化载体中使用两个字段或两列；不要把 `proposed / unverified` 合并塞进 `currentness` 一格。

| 当前性 | 中文说明 | 含义 |
|--------|----------|------|
| `proposed` | 提议 | 尚未被采用为当前规则 |
| `current` | 当前 | 已被明确采用为当前规则 |
| `superseded` | 已替代 | 不再是当前规则，只因迁移、历史引用或兼容需要保留 |

仅当内容存在验证要求或证据结论时，再记录验证性：

| 验证性 | 中文说明 | 含义 |
|--------|----------|------|
| `unverified` | 未验证 | 尚无足以支持或否定该结论的验证结果 |
| `supported` | 已支持 | 指定范围内已有可追溯证据支持 |
| `rejected` | 已否定 | 指定验证已否定该结论或触发失败条件 |

用户要求“先设计一个版本”但没有明确采用时，默认 `proposed + unverified`。用户明确采用但仍需试玩或数据验证时，写 `current + unverified`。标为 `current` 不自动意味着 `supported`；同样，验证结果也不能代替当前性决策。

尚未采用的提案连续改稿时，更新同一份最小 `proposed` 切片，由版本历史保留 A/B/C 变化；旧草稿既不是 `current`，也不要误标为 `superseded` 或 `rejected`。只有曾经成为当前规则的内容被新规则替代时才使用 `superseded`，只有证据命中失败条件时才使用 `rejected`。

状态用于保护设计基线，不是策划正文的组织轴。目标权威已有 YAML、表格或固定字段时，在原位置准确记录一次；没有既定 schema 时，不为状态新建 YAML frontmatter、开场状态表或独立章节，也不要在边界、结论和回退章节重复声明。会话内评审稿若必须说明成熟度，用一句自然语言注明“待采用 / 待验证”即可，正文先展开本次真正设计的对象与规则。

## 三种影响范围

`concept`、`system-map`、`feature` 是同一次变化可能命中的不同范围，不是必须依次完成的阶段。一次变化可以命中一个或多个范围；只更新实际发生变化的部分。

| 范围 | 何时命中 | 必读 reference |
|------|----------|----------------|
| `concept` | 目标玩家、体验承诺、核心循环或顶层边界改变 | `references/concept.md` |
| `system-map` | 新增、删除、改名、拆并系统，或系统职责、所有权、输入输出、依赖改变 | `references/system-map.md` |
| `feature` | 某个系统或功能切片的触发、行为、状态、反馈、失败恢复或验收改变；日常规则修改默认从这里开始 | `references/feature-rules.md` |

口语“做 / 设计某系统”通常先写该系统的 `proposed` 功能切片；只有系统登记、边界或依赖也发生变化时才同步 `system-map`。功能提议不以概念案或系统地图完整为前提，系统地图也不以列齐整款游戏为目标。

## 写入边界

- 正文只承载设计内容及必要的状态元数据；状态只在对应条目记录一次，不替代设计层级、对象、规则或内容结构。本次只修改必要差量并保留未触达基线，不复述调查过程或候选推演。其中只有标为 `current` 的子集属于当前设计基线。
- 用户给出方向但尚未明确采用，或只是要求起草时，写 `proposed`；若必须在多个高影响真实候选中作选择，才把该决策交 `design-inference`。
- 同一提案在采用前反复变化时原位修订最小切片，不并列累积多份“当前方案”；真正需要保留和比较多个高影响候选时，把候选集交 `design-inference`，这里不把候选写成多份权威。
- 验证字段按风险补充：低成本、尚未采用的提案改稿通常只更新验证问题，不强制展开阈值、复查日程和备选方案；已采用、高返工、不可逆或即将进入实现 / 发布的 `unverified` 规则才需要明确观察信号、复查时机和回退。
- 事实缺口只有在会实质改变本次规则时才阻断相应部分，并交 `design-evidence`；其余未知项按 `proposed` 假设保留，命中验证问题时另记 `unverified`。
- 不为补齐规则或回退凭空发明旧机制、默认值、触发条件或兼容行为。来源未给出时省略、标为未知，或只写“恢复到最后一个已确认基线”，不能把猜测写成原有 `current`。
- 版本 P0-P3、产品 MVP、日期、人员和里程碑属于版本规划，由 `design-workflow` 管理，不写入永久系统权威。
- 功能规则可以包含行为成立所需的常量、输入、玩家反馈和显示语义；技术架构、类名、目录和具体实现由实现方决定。

## 稳定标识

稳定 ID 是跨边界引用工具，不是文档完整度指标：

- 已有 `SYS-*` / `RULE-*` 被代码、配置、测试、遥测、任务或其他维护文档引用时，保留并沿用。
- 新内容只有在上述外部消费者需要稳定引用时才分配 `SYS-*` / `RULE-*`；同一局部文档内用清晰标题或表格行即可。
- 不为补齐编号批量创建占位 ID，不因改名重编号。
- 删除或拆并已被外部引用的内容时，保留原稳定 ID、标为 `superseded`，并记录替代项、真实消费者和移除条件；只写模糊“旧标识”不算完成。无外部引用时可直接删除，不强制保留墓碑。

## 流程

1. 确认本次动作是新增、修改还是删除，并定位当前设计基线及直接受影响的段落；若不存在，只建立最小切片。
2. 标记当前性；只有命中验证问题时才另记验证性。状态写在元数据或受影响条目，不用来组织正文。选择实际命中的一个或多个影响范围，不要先补齐未命中的上层或邻接文档。
3. 检查现有外部引用，据此决定保留或分配稳定 ID。
4. 只读取命中范围及确有需要的条件 reference，然后做局部修订。
5. 对改动执行一致性和行为验收检查；把尚未证明的假设留在改动附近，并只在风险需要时补复查时机与回退条件。
6. 只列真实受影响的下游同步项。需要版本编排、跨团队门槛或完整快照时再交 `design-workflow`。

## 完成标准

- 用户要求的新增、修改或删除已在设计权威载体中清楚可见，并有准确当前性；只有 `current` 子集进入当前设计基线，命中验证问题时另有准确验证性。
- 只更新真实受影响范围，没有为追求完整度虚构概念、系统、依赖或规则。
- `proposed` 与 `current` 可区分；`unverified` 的验证问题可见，已采用、高返工、不可逆或临近交付时才要求完整复查与回退闭环。
- 外部引用需要的稳定 ID 被保留或完成替代说明；不需要外部引用的内容没有被迫编号。
- 新增细节和回退基线都能回到用户输入、当前权威或明确假设，没有把合理猜测伪装成原有事实。
- 正常、边界、失败或删除影响按本次范围得到可观察验收，没有把推论或实现细节伪装成当前设计。
