# `feature`：功能规则切片

日常新增、修改或删除某个系统内部行为时默认使用。功能规则可以独立成为 `proposed` 提议，不要求先有完整概念案、`SYS-*` 或系统地图；只有边界和跨系统依赖也改变时才同步 `concept` 或 `system-map`。

## 可写范围

- 触发、前置条件、行为结果、限制和优先级。
- 对象、字段语义、流程、状态、事件和不变量。
- 玩家反馈、失败、取消、重试、恢复和不可逆保护。
- 跨系统输入输出、责任边界与可观察验收。
- 规则成立所需的常量、输入方式、反馈和显示语义。

不指定类名、目录或技术架构。经济模型、页面结构或交互规格只有在其本身就是本次设计规则时才写入；否则只记录必须满足的行为契约。

## 策划对象优先

先确定本次主要设计什么，再选择字段。正文按策划对象的内部结构展开，不按玩家感受、当前性、验证性或项目治理组织；这些内容分别作为结果校验、元数据或外部约束出现。

| 主要策划对象 | 需要闭合的结构 |
|--------------|----------------|
| 系统 / 机制 | 对象、状态、事件、规则因果、跨系统关系、不变量、异常与反利用 |
| 关卡 / 遭遇 | 目标与约束、空间拓扑、信息与门控、事件顺序、失败恢复、变化参数与灰盒验证 |
| 数值 / 经济 | 变量与单位、公式或流量关系、参数初值、示例演算、边界与反利用、调参旋钮与验证组合 |
| 叙事 / 内容单元 | 内容职责、进入条件、顺序或分支、状态标记、失败替代、复用规则与内容变化边界 |

普通差量只补本次命中的字段；用户明确要求首版完整方案、团队评审、灰盒制作或继续拆成功能案时，才保证主要对象形成上述最小闭环。一次选择一个主要对象，只有真实依赖才补其他对象，不能把本表扩成每次必填的完整 GDD。

## 差量规则

- 先记录本次动作、状态和直接修改点，不为单条变化重写整个系统。
- 新规则没有外部消费者时使用清楚标题或表格行；被代码、配置、测试、遥测、任务或其他维护文档引用时才分配 `RULE-*`。
- 修改已有 `RULE-*` 时保留 ID，并说明行为兼容或迁移影响。
- 删除无外部引用的规则可以直接移除；仍被引用时标为 `superseded`，记录替代规则、消费者和移除条件。
- 用户要求先形成方案但尚未明确采用时写 `proposed + unverified`；已明确采用但需要试玩或数据证明时写 `current + unverified`。采用为 `current` 不自动改成 `supported`。

## 按需字段

只选择与本次行为有关的字段，不强制生成状态机、事件表或异常矩阵：

| 字段 | 记录内容 |
|------|----------|
| 变化摘要 | 新增 / 修改 / 删除什么，当前性与直接来源；验证相关时另记验证性 |
| 目标行为 | 玩家或系统在何种情境下应获得什么结果 |
| 触发与条件 | 谁在何时触发，必须满足和不得满足什么；来源未定义开始、结束或取消条件时明确标为未知 / 待确认，不凭反馈事件或状态名称补猜 |
| 结果与限制 | 状态、资源、反馈如何变化，优先级和次数边界 |
| 失败与恢复 | 失败原因、反馈、取消、重试、恢复和不可逆保护 |
| 跨系统契约 | 输入、输出、责任方和消费者 |
| 行为验收 | 正常、边界、失败、恢复或删除后的可观察结果 |
| 验证与回退（按风险） | `unverified / supported / rejected` 与验证问题；已采用、高返工、不可逆或临近交付时再补证据、复查时机和失败回退 |

## 按需读取

- 当前采用或明确提议的教学、挑战、提示或节奏规则：`feature/experience-pacing-flow.md`
- 当前采用或明确提议的瞄准、QTE、命中框或操作精度规格：`feature/input-precision-control.md`
- 当前采用或明确提议的 PVP、合作、交易、克制或收益规则：`feature/strategic-interaction-payoff.md`
- 需要进入团队评审后继续拆功能案、灰盒 / 配置搭建，或把行为契约交给实现方时：`feature/execution-handoff.md`

这些 reference 只提供写入字段、一致性和验收检查。候选取舍达到 `design-inference` 的高影响或高返工升级门槛时再交接；低成本可逆比较在当前变化中内联判断。需要专项证明真实表现时交 `design-evidence`。

## 一致性与验收

- 本次规则是否仍在当前系统边界与有效概念约束内；若边界也改变，是否同步对应影响范围。
- 触发、条件、结果、限制、反馈和恢复是否足以解释本次变化，不要求补写无关流程。
- 用户要求开始 / 结束反馈但没有给出状态如何开始或结束时，是否已把触发源和结束条件单独标为未知或待确认，而不是把反馈本身当成生命周期规则。
- `proposed` 是否与 `current` 区分，验证问题是否可见；风险需要时是否补足观察信号和回退，当前性与验证性没有互相替代。
- 修改或删除是否处理了真实外部消费者，而非为假想完整性创建引用。
- 是否把候选取舍、证据调查、版本优先级或实现架构混入当前规则。
- 公式或数值关系是否检查 `0 / 关闭态`、最小值、最大值、截断、最低成本与倍率组合，避免单项语义正确但组合后互相矛盾。
- 存在总时限、后置准备或多个阶段时，成功 / 失败表达式是否唯一，阶段进入、退出、并行、重入与不可逆点是否互相一致。
- 关卡节点、内容变化或恢复分支是否都引用已定义对象，并能对应到消费规则和至少一个验收场景。
- 批次、队伍、库存、耐久等带数量的集合对象是否明确完整成功、允许损失或降级成功、硬失败与终止后的结算阈值；本轮不允许部分损失时应直接写明，而不是只定义“全部归零”。
