# 功能实现交接

仅在用户明确要求把当前功能规则整理为实现可消费的行为契约时读取。交接是源规则的差量投影，不冻结设计，也不替程序决定架构；后续规则变化应更新源设计及受影响交接项。

## 写入边界

- 只交接本次新增、修改或删除影响到的行为、数据语义、依赖和可观察结果。
- 设计引用优先使用现有标题或链接；只有实现、配置、测试或其他外部消费者需要稳定引用时才要求 `SYS-*` / `RULE-*`。
- 规则成立所需的范围、单位和默认值可以内联；未采用数值保持 `proposed`，已采用但尚未验证的数值写 `current + unverified`。
- UI 只记录玩家必须理解的事件、原因、结果和下一步，不创建页面、控件或导航方案。
- Unity 资源只写影响类型、必需语义和验证点；实际修改仍遵守项目 Unity 规则。
- 版本优先级、MVP、发布日期、人员、里程碑和发布门槛交 `design-workflow`；测试结果交 `design-evidence`。

## 一致性与验收

- 交接项是否能逐项追溯到源规则的当前性；验证相关时是否另有验证性与证据引用。
- 删除、改名、拆并是否列出真实消费者、替代项和移除条件。
- 数据、状态、事件和资源语义是否足以验收，但没有指定未经授权的实现架构。
- 若交接暴露概念约束、系统边界或依赖也发生变化，同步对应影响范围；不要把它解释成必须回到某个“上层阶段”。
