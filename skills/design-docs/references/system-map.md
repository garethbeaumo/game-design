# `system-map`：稀疏系统注册表与依赖图

只在新增、删除、改名、拆并系统，或系统职责、设计所有权、输入输出、依赖发生变化时更新。它是随项目演进持续维护的稀疏索引，不要求列齐整款游戏，也不是功能设计的前置阶段。

## 可写范围

- 当前已知系统的名称、状态、单一职责和玩家可见贡献。
- 系统拥有的规则域、状态或资源语义，以及它不负责什么。
- 系统输入、输出、上游依赖和下游消费者。
- 系统新增、删除、改名、拆分、合并后的替代关系和同步对象。
- 指向详细功能规则的链接。

版本 P0-P3、产品 MVP、发布日期、人员、里程碑和实现顺序属于 `design-workflow` 的版本规划，不进入本注册表。这里不重新选择体验承诺，也不展开系统内部行为规则。

## 稀疏原则

- 只登记当前变化触达或已有外部消费者需要定位的系统，不为展示“完整架构”创建占位系统。
- 功能规则可以先于系统登记存在；当职责边界或跨系统依赖需要稳定表达时再补注册表。
- 系统缺少概念上游引用不阻断登记；未采用的新条目标为 `proposed`，验证相关的未知项另记 `unverified`。
- 依赖图只记录会影响设计行为或责任归属的边，不复制代码调用图和团队组织图。

## 系统条目

按本次变化选用字段：

| 字段 | 记录内容 |
|------|----------|
| 名称 / 稳定 ID | 可读名称；只有存在外部引用时才需要 `SYS-*` |
| 当前性 | `proposed / current / superseded` |
| 验证性（按需） | 仅在边界或依赖需要验证时记录 `unverified / supported / rejected` |
| 单一职责 | 本系统唯一拥有的设计责任 |
| 玩家可见贡献 | 它为哪段体验或循环提供什么结果 |
| 所有权边界 | 拥有哪些规则、状态或资源语义；明确不拥有什么 |
| 输入 / 输出 | 接收什么设计语义，产出什么可消费结果 |
| 依赖 / 消费者 | 必须依赖谁，结果被谁使用 |
| 详细规则 | 指向 `current` 或 `proposed` 功能规则的链接 |
| 未知与验证 | 仅记录会改变边界或依赖的未知项 |

## 关系变更

- 新增：只增加新系统及与现有系统直接相关的边。
- 修改或改名：保留被外部引用的稳定 ID，更新职责、边或显示名称。
- 拆分或合并：记录旧项到新项的替代关系、规则 / 状态所有权迁移和待同步消费者。
- 删除：无外部引用时直接删除；仍有消费者时先标为 `superseded`，记录替代项和移除条件。

## 一致性与验收

- 每个登记系统是否只有一个清楚的主职责；重叠所有权是否明确裁定或标为待决。
- 输入、输出和依赖边的两端是否使用相同语义，是否有无人拥有的关键状态或资源。
- 本次新增、删除、改名或拆并是否同步了真实消费者和详细规则链接。
- 当前性和替代关系是否足以让外部引用方判断当前应使用哪个系统；验证性没有被当作采用决策。
- 是否误写了 P0-P3、产品 MVP、制作排期、内部规则细节或技术调用关系。
