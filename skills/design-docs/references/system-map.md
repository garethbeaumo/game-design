# `system` 模式：系统地图与产品 MVP

把已确认的核心动作循环和顶层边界映射成单一职责系统、依赖关系与最小可发布闭环。

## 权限

- 写入 `SYS-*`、系统职责与边界、输入输出、依赖、P0-P3、产品 MVP、系统级切片，以及不含数量参数的资源所有权与流向。
- `concept` 模式产物、`DEC-*`、Prototype 结论、规模证据和制作硬约束是只读上游。
- 不重新选择体验支柱或核心动作循环，不写系统内部 `RULE-*`、实现架构、里程碑日期或人员安排。

## 工作原则

- 按玩家体验链路映射职责，不按脚本目录、现有代码或团队分工猜系统边界。
- 每个 `SYS-*` 只有一个主职责，并能追溯到循环节点或顶层承诺。
- P0 表示缺少就无法完成产品 MVP 闭环；P1 影响主要体验但可后补；P2 增强深度或内容量；P3 为长期扩展。
- 系统边界、产品 MVP 或关键依赖仍有互斥取舍时回 `design-inference`；阻塞分支未确认时使用 `grill-me`。
- 已有地图只修改受影响的 `SYS-*`、依赖和优先级。

## 上下文

1. 读取当前概念、核心动作循环、顶层边界和相关 `DEC-*`。
2. 读取已有系统地图、Prototype 证据和可信规模锚点。
3. 实现现状只作为 `design-evidence` 提供的事实，未经确认的目录或组件不是系统边界。
4. 缺少已确认核心循环或范围时停止拆图，转 `concept` 模式或 `design-inference`。

## `standard` 核心骨架

1. **范围与上游引用**：引用概念、核心动作循环和决策，不复制推论过程。
2. **系统清单**：`SYS-*`、单一职责、体验问题、循环节点、输入输出、依赖和状态。
3. **产品 MVP 与 P0-P3**：最小闭环、P0 的最小职责、P1-P3 和明确不进入当前版本的内容。
4. **依赖与设计顺序**：串行依赖、循环依赖、可并行项和集成前提；不写日期或人员。
5. **边界风险**：职责重叠、所有权不明、依赖未定、系统过大或循环无法闭合的问题。

## 条件模块

- **循环映射**：把既有动作节点映射到 `SYS-*`，不得改变动作语义。
- **定性资源拓扑**：资源所有者、来源、去向、积累池和断头风险；只记录规则需要的定性关系。
- **内容切片**：最小阶段、内容对象类别、门控责任和复用责任；内部规则交 `feature` 模式。
- **版本切片**：Prototype 结论如何进入产品 MVP、Vertical Slice 或后续版本，不写制作排期。
- **接口摘要**：跨系统输入输出与责任归属；事件、状态和异常细则交 `feature` 模式。

## 自检

- 每个 `SYS-*` 是否只有一个主职责且可追溯到上游。
- 产品 MVP 是否闭环，P0 是否真的不可缺少。
- 输入输出、所有权和依赖是否存在重叠或未解释循环。
- 是否误写候选决策、内部规则或制作排期。
