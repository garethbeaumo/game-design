# 约束与决策矩阵

在 Phase 1 约束分析、重大方案取舍、竞品借鉴是否适配、或用户问“值不值得做”时使用。目标是把直觉判断转成可复查的约束、证据和结论。

## 使用顺序

1. 先确认显性约束。
2. 再交叉推导派生约束。
3. 标注硬约束、软约束和伪约束。
4. 对候选方案填写决策矩阵。
5. 输出待确认问题；如果用户修正关键约束，回到第 1 步重推。

## 显性约束

显性约束不是“分析出来的猜测”，而是设计开始前必须确认或声明默认假设的前提。

如果品类、游戏类型、时间投入、付费预期、留存 / 流失模型或品类 × 类型交叉推导不清，继续读取 `genre-type-constraint-matrix.md`。

| 约束 | 必须回答 | 不确定时的风险 |
|------|----------|----------------|
| 品类 | 玩家核心乐趣是什么，主要在玩什么 | 方案都看似可行，但没有取舍标准 |
| 游戏类型 | 手游 F2P、单机买断、端游长线、小游戏、订阅、买断 + 长线服务等 | 时间投入、付费心理和流失模型判断错误 |
| 平台与输入 | PC、移动端、手柄、触屏、键鼠 | 操作复杂度、UI 密度和反馈节奏失真 |
| 目标用户 | 新手、休闲、核心、社交、收集、竞技等 | 难度、节奏、信息量和学习曲线错位 |
| 单次时长 | 一局、一次循环、一次会话的目标长度 | 核心循环过长或过碎 |
| 内容规模 | 对标的具体已上线游戏和预期游玩时长 | 系统深度和内容量失控 |

## 派生约束

显性约束确认后，必须至少推导以下四类约束。

| 派生约束 | 推导问题 | 输出 |
|----------|----------|------|
| 驱动力可行性 | 品类需要什么驱动力，游戏类型能支撑什么驱动力 | 主驱动力、副驱动力、不可行驱动力 |
| 循环节奏 | 品类自然循环长度和单次时长是否匹配 | 核心循环目标时长、压缩或展开方式 |
| 流失关注点 | 玩家会因内容枯竭、深度不足、挫败还是等待流失 | 重点风险、干预时机、验证指标 |
| 体验取舍 | 哪些体验必须保留，哪些可以延后，哪些不该做 | 必须保留 / 可延后 / 不做 |

品类与游戏类型交叉推导必须落到后续产物：
- 驱动力可行性影响 `design-inference` 与 `design-docs` 的 `concept` 模式。
- 循环节奏影响 `design-docs` 的 `concept`、`system` 与 `feature` 模式。
- 流失关注点优先形成 `design-evidence` 的 `playtest` 证据，再由 `design-inference` 或 `design-docs` 处理。
- 产品优先级由 `design-docs` 的 `system` 模式维护，制作阶段与里程碑由 `design-workflow` 维护。

## 约束分级

| 类型 | 定义 | 处理方式 |
|------|------|----------|
| 硬约束 | 已确认上层文档、客观平台限制、预算工期硬边界 | 必须遵守；冲突时回查上层 |
| 软约束 | 上层倾向、风格偏好、阶段性目标 | 可以违背，但要说明代价和收益 |
| 伪约束 | 现有实现、历史习惯、口头决定、竞品惯例 | 不能直接继承；标记后走推论确认 |

技术现状、当前架构和“可能难做”默认不是玩家价值判断。先判断方案是否有独特乐趣、学习点和顶层支持，再把实现成本转成硬约束、软约束、伪约束、Prototype 缩小验证或交给 `design-docs:system` 的范围问题。

## 常见说法诊断

遇到未经拆解的理由时，先自问，不直接定案。目标不是推翻想法，而是定位它解决的真实需求、证据和风险。

| 原始说法 | 自问 | 诊断方向 |
|----------|------|----------|
| 参考某游戏 | 它解决的是哪类用户的什么需求，我们的目标玩家有同样需求吗 | 需求匹配度，不是功能照搬 |
| 玩家肯定喜欢 | 这满足什么玩家需求，需求强度、普遍性和证据是什么 | 需求真实性 |
| 功能更丰富 | 它解决什么问题，现有系统是否已满足部分需求 | 需求冗余和范围膨胀 |
| 数值调一下就好 | 数值问题背后是否是规则、循环、反馈、节奏或目标玩家不匹配 | 症状 vs 根因 |
| 竞品这么做 | 竞品用户、品类、商业模式和规模锚点是否与我们一致 | 品类需求差异 |
| 当前实现就是这样 | 这是已确认设计约束，还是当前代码、原型或历史习惯 | 伪约束识别 |

## 决策矩阵

用于判断方案是否进入下一阶段。矩阵不是打分游戏，关键是写证据和结论。

| 维度 | 判断 | 证据问题 | 结论规则 |
|------|------|----------|----------|
| 有趣度 | 高 / 中 / 低 | 玩家能学到新规律、新组合、新表达或新目标吗 | 低则放弃或重做乐趣来源 |
| 差异化 | 高 / 中 / 低 | 它只是竞品标配，还是强化了本项目独特体验 | 低但必要时降为基础能力 |
| 生命周期 | 长期 / 中期 / 过渡 | 新手期后还需要它吗，三个月后还有价值吗 | 过渡内容避免做成重系统 |
| 顶层支持 | 强化 / 中性 / 偏离 | 它强化哪个设计支柱，削弱哪个上层目标 | 偏离是一票否决，先回查上层 |

实现成本不作为独立否决维度；它只决定验证方式和落地阶段。只有违反已确认平台边界、法律合规、预算工期硬边界或上层范围的内容，才能作为硬约束否决。
