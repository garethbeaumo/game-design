# 设计层级与五入口边界

当需求层级不清、内容混杂或多个 Skill 看似都能处理时读取。

## 总原则

- 证据说明“发生了什么”，决策说明“为什么这样选”，正式设计说明“当前规则是什么”，治理说明“谁在何时交付什么”。
- 高层决定方向和边界，低层决定规则；实现现状不能替代设计约束。
- 同一请求默认只有一个主责 Skill 和一个主要产物。
- 下层与上层冲突时先记录冲突，再决定回到 `design-inference` 重选，还是由 `design-docs` 修订对应层级。

五入口的触发、写入权限与冲突裁定只维护在 `../../design-workflow/references/routing-matrix.md`；本文件不复制第二份职责表。

## `design-docs` 内部层级

| 模式 | 回答什么 | 不应在本层决定 |
|------|----------|----------------|
| `concept` | 玩家、体验承诺、支柱、核心动作循环和顶层边界 | 系统清单、P0-P3、状态机和实现细节 |
| `system` | 系统职责、依赖、P0-P3 和产品 MVP | 重新选择核心体验、系统内部状态与事件 |
| `feature` | 对象、触发、流程、状态、事件、不变量和行为验收 | 重新定义概念、系统边界和制作排期 |

## 常见跳层

| 现象 | 问题 | 处理 |
|------|------|------|
| 证据报告直接写“项目应采用” | 用事实入口替项目拍板 | 交 `design-inference` 形成 `DEC-*` |
| 决策记录直接成为当前规则 | 候选与权威未分离 | 确认后交 `design-docs` 对应模式落档 |
| 概念案开始写系统状态机 | 执行细节提前锁死方向 | 拆到 `system` 或 `feature` 模式 |
| 系统地图写大量内部字段与异常流程 | 系统职责和内部规则混写 | 拆到 `feature` 模式 |
| 功能案用“当前代码如此”作为规则 | 把实现现状当硬约束 | 先用 `design-evidence:implementation` 固化事实，再判断是否采纳 |
| Prototype 追求完整产品内容 | 验证目标失焦 | 只保留验证致命假设的最小交互 |
| 里程碑直接改变产品 MVP | 制作计划越权改设计 | 回 `design-docs:system` 修订，治理只安排执行 |

## 使用方式

- 缺少可复查事实或输入仍是原始材料时，先按路由矩阵交 `design-evidence`。
- 已有 `EVID-*`，需要界定设计问题或比较候选时，才进入 `design-inference`。
- 已确认结论需要成为当前设计时进入 `design-docs`，再使用上表选择内部模式。
- 其余入口冲突直接回路由矩阵裁定，不在本文件新增规则。

## 输出裁定格式

```markdown
## 层级裁定
- 当前问题类型：证据 / 决策 / 正式设计 / 治理 / 澄清
- 唯一主责 Skill：
- 模式（如适用）：
- 可写权威：
- 本次不处理：
- 后续交接：
```
