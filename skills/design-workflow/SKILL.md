# 游戏策划迭代治理

以一次可验证、可回退的设计变更为治理单位。治理负责顺序、责任和版本出口，不替专项 Skill 调查事实、完成取舍或写游戏规则。

## 模式

| 模式 | 何时使用 | 不应附加 |
|------|----------|----------|
| `governance` | 版本范围、多人责任、关键路径、迁移、审批或发布出口需要统一协调 | 未受影响的系统细节和整项目重规划 |
| `snapshot` | 用户明确要求按当前权威生成完整 GDD / full-package 或评审快照 | 新负责人、日期、门槛、回退或任何新规则 |

`snapshot` 是只读投影，不是轻量版 `governance`，也不建立 change-set。

## 边界

- 管理需要版本、多人责任、审批、迁移窗口或发布出口统一协调的 change-set。
- 只读证据、决策、当前设计和实现状态；通过稳定 ID 或链接引用，不复制第二套规则。
- 单个设计切片直接交 `design-docs`；事实确需调查时交 `design-evidence`；候选取舍达到 `design-inference` 的高影响或高返工升级门槛时再交接。若调查或取舍由活跃 change-set 发起，结果回到该 change-set 继续治理；只有同时确认要改游戏规则时才另交 `design-docs`。
- 完整 GDD / full-package 只是从当前权威生成的只读快照，不是新的事实所有者。
- 策划 Skill 自身的职责、触发、测试和生成属于外部控制面，不是游戏版本治理。

## 流程

1. 按入口边界选择 `governance` 或 `snapshot`，而非把单项设计或 Skill 自维护包装成治理。
2. `snapshot`：只投影实际可定位的当前概念、系统注册表、功能规则及已有版本范围，每个条目带来源和生成时间，并保留 proposed / current、验证性和来源中的未知项。若没有提供或找不到实际权威正文 / 路径，只简洁列出缺失的来源类别后停止；不能把“本轮无法读取”断言成“项目没有设计”，也不要生成一套空的 P0、负责人、门槛或回退表。不得创造任何治理字段或新规则。
3. `governance`：定义本次 change-set 的目标版本、当前基线、受影响范围、明确不改内容和关闭条件。
4. 只登记需要统一协调的负责人、关键路径、迁移窗口或版本出口；纯设计依赖与局部细节留在拥有它的设计文档。
5. 按风险决定是否需要证据、决策、系统注册表、功能规则或额外验证；委托完成后返回当前 change-set，不强制走固定阶段链。
6. 写清受影响事项的负责人、审批者、最晚确认时机、可观察出口和失败回退。
7. 活跃 change-set 的范围、P0-P3 或负责人变化时，在同一版本记录中重新基线化并保留差量，不复制整份计划或并列多份当前版本；只复核被该变化触达的关键路径、责任交接、验证 / 发布出口和失败回退，未受影响项直接沿用，不要求逐项抄写“不变”。范围取消或优先级变化不自动清空、替换负责人；只有用户、当前权威或明确组织规则给出责任变化时才修改，取消项仍可能需要原负责人完成收尾、迁移或归档。
8. 通过后只更新受影响权威；失败则回退或进入下一轮 change-set，不为保持文档完整而扩写范围。

## 按需读取

- change-set、状态、稳定 ID 与归档：`references/artifact-standards.md`
- 交付深度：`references/artifact-output-profiles.md`
- 实现、验证、合入或发布是否就绪：`references/stage-gates.md`
- 版本范围、里程碑和关键路径：`references/milestone-production-planning.md`
- 多负责人、审批和协作冲突：`references/team-collaboration-governance.md`

## 完成标准

- `governance` 只有一个治理目标和一组边界明确的 change-set，而不是完整项目重规划。
- 活跃版本发生裁剪、优先级或责任变化后，仍只有一份最新基线；变化原因、关键路径、责任交接、可观察出口和回退的受影响部分均可追溯。
- 每个受影响范围只有一个当前权威，提案和实验不会伪装成当前规则。
- 依赖、负责人、验证、关闭条件和回退可复查。
- `snapshot` 的每个投影条目都能回到实际来源并标明时间、状态与未知项；缺少来源时只报告来源缺口，没有搭建空治理框架、凭空补字段或成为第二套游戏设计。
