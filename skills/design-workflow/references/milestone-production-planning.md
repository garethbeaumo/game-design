# 版本与里程碑治理

用于 change-set 进入版本范围，并需要处理资料片、持续运营、里程碑、关键路径或发布出口时。里程碑证明一个版本目标，不假定项目只经历一次 Concept → Release 生命周期。

需要处理共享愿景、决策权或跨工种冲突时，继续读取 `./team-collaboration-governance.md`。

## 版本范围

- 先定义版本要验证或交付的玩家结果，再选择 change-set。
- P0-P3 是当前版本或里程碑的范围标签，不是系统永久属性：
  - P0：没有它，本版本目标无法成立。
  - P1：本版本主要体验所需。
  - P2：有价值但可降级或延后。
  - P3：探索、候选或未来扩展。
- 同一系统可以在不同版本拥有不同优先级；系统注册表只保存职责、接口、依赖和状态。
- 明确纳入、延后、不做和替代项，避免用模糊“之后补全”掩盖范围。

## 迭代类型

| 类型 | 目标 | 典型出口 |
|------|------|----------|
| 探索 / Prototype | 验证致命假设 | 观察、通过/失败标准、回退决定 |
| Vertical Slice | 证明目标品质和跨工种流程 | 可玩切片、资源管线、集成证据 |
| 版本增量 | 新增或修改可交付玩家价值 | change-set 完成、回归和兼容检查 |
| 内容/资料片 | 扩展内容或系统组合 | 依赖、迁移、产能和目标玩家验证 |
| 持续运营 | 调整数值、活动、赛季或长期系统 | 指标护栏、灰度、监控和回滚 |
| 发布 / 热修 | 安全交付当前基线 | 阻塞清零、目标环境验证和回退预案 |

这些类型可以重复、嵌套和回环；Alpha/Beta/Release 只在项目确实采用该生命周期时使用。

## 活跃版本再基线化

版本开发中发生范围裁剪、P0-P3 调整、依赖变化或负责人替换时，更新同一份活跃 change-set：先记录变更原因和原基线，再改动受影响条目，并沿真实依赖只复核被触达的关键路径、责任交接、验证 / 发布出口和回退。若复核后某个受影响字段不变，在该差量附近简记结论与理由；完全未受影响的字段直接沿用，不要求逐项抄写“已复核、不变”。最新内容是唯一当前版本基线；旧值由差量记录或版本历史追溯，不复制整份计划，也不重写未受影响的系统与规则。

## 里程碑字段

| 字段 | 要求 |
|------|------|
| 版本目标 | 玩家或验收者最终能获得什么 |
| 当前基线 | 从哪个版本、系统状态或规则集开始 |
| change-set | 本次纳入的新增、修改、废弃和迁移 |
| 范围标签 | 当前版本的 P0-P3、延后和不做 |
| 关键路径 | 不能并行或会阻塞后续的依赖 |
| 验证方法 | Prototype、试玩、自动测试、编辑器、目标环境或人工检查 |
| 负责人 | 推动者、审批者、被咨询者和被通知者 |
| 风险与回退 | 触发信号、影响、降级和回滚 |
| 出口 | 可复查证据，不能只写“完成” |

再次基线化时只重算受影响条目的范围标签，以及被真实依赖触达的关键路径、负责人、验证 / 发布出口与回退；其他字段沿用当前基线。P0 变化至少复核对应关键路径、验证 / 发布出口与回退，负责人变化至少复核交接与出口归属；未触达的字段无需追加无变化声明。范围取消或优先级变化本身不是解除责任的依据，负责人只有在用户、当前权威或明确组织规则给出变更时才改；取消项的原负责人可继续承担收尾、迁移或归档。

## 关键路径检查

- 是否有未验证假设阻塞多个 change-set。
- 是否有系统接口、资源、工具、配置或场景引用阻塞多个工种。
- 是否把需要先验证的手感、控制或反馈推迟到高成本阶段。
- 是否把必须串行的迁移写成并行，或把可以独立验证的工作绑成大包。
- 是否存在多个事实所有者、隐含否决权或无人负责的回退。

## 完整设计快照

用户明确要求完整 GDD / full-package 时，从当前概念、系统注册表、功能规则和版本范围生成只读索引或快照。快照标明生成时间和来源，不成为新的可独立修改权威。
