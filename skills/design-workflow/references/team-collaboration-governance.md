# 团队协作与决策治理

用于 change-set 需要多人共享目标、职责、审批、交接或冲突升级时。纯设计结构拆并和局部规则无需为了模板补齐团队矩阵。

## 使用原则

- 每个受影响范围只有一个当前权威，每个 change-set 只有一个推动负责人和最终审批入口。
- 多人可以提供证据和专业限制，但不能隐藏多个互不透明的否决权。
- 先判断冲突属于事实、取舍、当前规则还是版本治理，再交对应 Skill。
- 状态、事实和开放问题优先异步记录；会议只解决需要同步判断的事项。
- 高影响变化保留依据、放弃项、验证信号和回退；普通局部变化依赖当前文档差量和 Git 历史即可。

## 决策角色

| 角色 | 职责 |
|------|------|
| 负责人 | 推动 change-set，维护状态、依赖和开放问题 |
| 最终审批者 | 决定是否合入当前设计或版本范围 |
| 被咨询者 | 提供实现、内容、表现、测试和制作限制 |
| 被通知者 | 接收已确认变化、迁移和回退信息 |

## 冲突分类与路由

| 冲突 | 推荐处理 |
|------|----------|
| 来源对竞品、测试或实现描述不一致 | `design-evidence` 补来源、快照和可信度 |
| 对玩家价值、系统方向或机制候选理解不同 | `design-inference` 比较真实候选与回退 |
| 当前概念、系统职责或功能规则互相矛盾 | `design-docs` 差量修订拥有冲突字段的范围 |
| 当前版本纳入范围、人员或关键路径冲突 | `design-workflow` 更新 change-set 和版本出口 |
| 只有口味分歧、无目标或证据 | 明确假设，必要时做最小 Prototype |

## 最小协作记录

| 字段 | 要求 |
|------|------|
| target | 本次版本或 change-set 目标 |
| owner / approver | 推动者与最终审批者 |
| consulted / informed | 必须提前咨询和同步的角色 |
| dependency | 跨系统、资源、工具或环境依赖 |
| escalation_trigger | 哪些信号需要升级判断 |
| acceptance / rollback | 合入条件与失败回退 |

## 反模式

- 用“大家都同意”代替明确审批者。
- 为每个小改动创建独立会议、DEC 和治理文档。
- 关键变化只在会议里说过，没有进入当前权威或 change-set。
- 反复讨论同一冲突，却没有新增证据、Prototype 或取舍标准。
- 用新增人力掩盖方向不清、关键路径或接口所有权问题。
